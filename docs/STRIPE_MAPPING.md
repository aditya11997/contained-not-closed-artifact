# Simulator ↔ Stripe test-mode mapping (WP5, hypothesis C1)

The adapter is `p4/adapters/stripe_test.py` and the conformance tests are `tests/conformance/test_stripe_vs_sim.py` (`@pytest.mark.stripe`; they run only with `STRIPE_TEST_KEY` set and `--run-stripe` or `P4_RUN_STRIPE=1`). The **documented** column cites the official Stripe docs, read on 2026-10-22, with the API version pinned to `Stripe-Version: 2026-09-30.endive` ([versioning](https://docs.stripe.com/api/versioning)). The **observed** column is produced by `python -m analysis.stripe_mapping <run dir>` from a live conformance run, never typed by hand. Its legend: ✅ observed and matches the sim · ❌ observed and does not match · *not tested*.

"Matches" means more than "same verdict". Both backends get identical payments and a logical `EventClock`, and the conformance test asserts that the two event logs are **line-for-line identical** (seq, t, type, uid, actor, key, result, so the hash chain matches too), that every reply agrees, and that the adapter recorded no anomaly.

## Adapter behaviour that rests on the docs (not separate transitions)

- **Keys**: sandbox secret keys start with `sk_test_` ([API keys](https://docs.stripe.com/keys), [authentication](https://docs.stripe.com/api/authentication)). The adapter refuses every other key, including `rk_test_`, and reads it only from `STRIPE_TEST_KEY`. Auth is HTTP Basic with the key as the username, over HTTPS only.
- **Key scope and lifetime**: keys "are up to 255 characters long", and Stripe may prune them "after they're at least 24 hours old" ([idempotent requests](https://docs.stripe.com/api/idempotent_requests)). Stripe scopes keys to the account, so the adapter namespaces them as `p4/<run_id>/<actor>/<key>`: per actor, as in the sim, and per run, so a rerun within 24 h can't replay an old run's response.
- **Not cached**: "If incoming parameters fail validation, or the request conflicts with another request that's executing concurrently, we don't save the idempotent result". Rate limiting also caches nothing ([low-level errors](https://docs.stripe.com/error-low-level)). The adapter therefore retries a `429`, or a `409` with `idempotency_key_in_use`, using the same key. It validates creates locally before sending (the sim's `INVALID_REQUEST`, not stored).
- **Rate limits**: "Sandbox: 25 requests per second" (global), per-endpoint 25/s, plus "1000 update requests per PaymentIntent object, per hour". The docs recommend "a client-side token bucket rate-limiting algorithm" ([rate limits](https://docs.stripe.com/rate-limits)). The adapter uses a token bucket at 8 requests/s with a burst of 4, and exponential backoff on `429`.
- **5xx**: "Treat the outcome of a request that returns `500` as indeterminate" ([low-level errors](https://docs.stripe.com/error-low-level)). The adapter maps any unmapped response to an error with no effect and records an anomaly, which fails the conformance test.

## Known differences (by design, stated as limitations)

- **Authorization expiry.** "Uncaptured PaymentIntents are cancelled a set number of days (7 by default) after their creation" ([capture](https://docs.stripe.com/api/payment_intents/capture)), and the card authorization windows run 5–7 days ([place a hold](https://docs.stripe.com/payments/place-a-hold-on-a-payment-method)). The sim has no expiry. Test runs last minutes, so this never triggers.
- **Capture time is emulated.** Merchant capture is our emulator calling capture at `D_actual` on the shared clock. Simulated capture times aren't card-network deadlines (CLAUDE.md rule 6). With the logical clock, the log records `CAPTURED` at `t = D_actual` and Stripe receives the capture before any later call. With `WallClockDriver` (`p4/sim/clock.py`, passed as `clock_factory=`), 1 sim unit = `unit_seconds` of wall time from the stop.
- **Amounts.** Stripe's minimum is "$0.50 US" ([create](https://docs.stripe.com/api/payment_intents/create)), and amounts are sent as cents. The sim has no minimum.
- **After capture.** Refunds and disputes exist on Stripe but aren't modelled. `CAPTURED` is absorbing, and that's a stated limitation (SCIENTIFIC_GUARDRAILS).
- **Reconciliation below the log.** If a request to Stripe really gets no response (a network error, not an injected fault), the adapter resends it with the same key and parameters before it writes the log line. If it still gets nothing, it aborts the run (`StripeUnavailable`) rather than write a log it can't vouch for.

**Two counts, not one.** The paper states both, and neither is typed by hand. `python -m analysis.stripe_mapping <run dir> --tex <file>` writes them as `\Stripe…` macros:
- *Mapping-table rows* (`\StripeMappingRows`, `\StripeMappingRowsMatched`): the rows of the transition table above. `TABLE_ROWS` in `analysis/stripe_mapping.py` names the outcome records each row rests on. A row is matched only if all of those records are present and matched.
- *Conformance tests* (`\StripeConformanceTests` = `\StripeTransitionScripts` + `\StripeEpisodes`): one per scripted transition and one per episode. `\StripeOutcomesRecorded` and `\StripeOutcomesMatched` come from `outcomes.jsonl`. `\StripeTestsRun` and `\StripeTestsPassed` come from `tests.jsonl` (pytest's own outcomes). Runs 1–3 have no `tests.jsonl`, so those two macros are not written for them.
