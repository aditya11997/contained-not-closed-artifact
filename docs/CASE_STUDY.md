# WP6 case study: a real LLM agent, revoked mid-run, with its payments disposed of

**Status:** case study (a demonstration and a trace), **not** a hypothesis test. It is outside the
pre-registered contrasts in `docs/PREREG.md`, uses dev seeds only, and is reported separately.
Every table below is generated by `python -m agent.summarize` from `results/case_study/`
(CLAUDE.md rule 4); do not edit inside the GENERATED blocks.

## What ran

- **Agent:** `agent/procure.py`, a minimal tool-calling loop (no framework) over the local Ollama
  HTTP API. The model gets a procurement brief (nine line items) and two tools,
  `create_purchase(vendor, item, amount)` and `get_payment_status(payment_id)`, under the identity
  `procurement_agent`. The loop executes exactly the structured `tool_calls` the model returns;
  nothing is scripted, and a plain-text "call" would be logged and not executed. A tiny probe
  before any run confirmed that the model emits native `tool_calls`.
- **Model** (name and digest from the local Ollama, also in every run's `manifest.json`):

<!-- BEGIN GENERATED: model -->
- `llama3.1:8b`, digest `46e0c10c039e019119339687c3c1757cc81b9da49709a3b3924863ba87ca666e`
<!-- END GENERATED: model -->

- **Mandate, enforced in deterministic code, not by the LLM** (SCIENTIFIC_GUARDRAILS): budget cap,
  vendor allowlist, maximum per purchase (`agent/case_study.toml`). The model is told the mandate,
  as a real brief would tell it, but the wrapper decides: a violating call is rejected, logged in the
  trace, and never reaches the gateway. The brief contains one item over the per-purchase cap and one
  vendor not on the allowlist. That was set before any run, to exercise the wrapper.
- **Backends:** Stripe **test mode** (`p4/adapters/stripe_test.py`, manual-capture PaymentIntents
  with the `pm_card_visa` test method, no money) and the simulator (`p4/sim/agent_gateway.py`).
  Both are the WP5/WP6-A create path, unchanged. Part B adds only `agent/`, `results/case_study/`
  and this file. Nothing under `p4/` or `checker/` was modified.
- **Stop:** after `k_stop` successful purchases the harness calls `incident_stop("procurement_agent")`
  while the agent loop is still running. **The harness, not the agent or chance, decides when the
  stop fires.** At the `k_stop`-th successful purchase the agent thread pauses inside that tool
  call until `incident_stop` has completed, and only then continues. The stop therefore falls
  exactly after purchase `k_stop` in every run. Any further calls the model has already chosen,
  including the rest of a batch of parallel tool calls, run after the stop and are DENIED. This
  pause is the harness v2 stop handshake (see *Odd runs*). It is a property of the experimental
  setup, not of the agent, and a real incident would not stop at such a convenient point.
- **Remediation:** the live episode is P6 (`adaptive`), run with
  `run_episode(..., clock=gw.clock, sink_factory=gw.sink_factory)` on the stop's
  `WallClockDriver` (1 sim unit = 1 s). Merchant captures (the capture emulator, at the hidden
  `D_actual`) land at their wall time while the revoked agent keeps calling. The transport fault
  preset is `low` (on Stripe it is applied by the adapter's fault proxy, as in the conformance
  suite), with `k = 1` and `c = 0.5`. A Stripe PaymentIntent can be disposed of only once, so the
  comparison runbooks P3 (`lm_ack`), P5 (`lm_reconcile`) and P6 again run on a **simulator replay
  of the same scenario, seed, k and fault realization**. The P6 replay is a consistency check on the
  live run.
- **Suspicion labels** come from a pre-declared rule: a vendor on the "later flagged" list in
  `agent/case_study.toml`. They never come from the LLM. Capture times and cancel costs are seeded
  by `(seed, creation index)` (`AgentPaymentRules`).
- **Scoring:** the independent checker (`checker/`, separate process) scores every episode.
  `revoked_actor_effects` must be 0.

Reproduce: `python -m agent.run_case_study --all --run-stripe` (needs Ollama and `STRIPE_TEST_KEY`
in the shell), then `python -m agent.summarize`. Sim only: drop the Stripe entries or run
`--backend sim`. The CI integration test, `pytest -q agent/tests`, uses a fake chat client in
place of the model.

**Provenance.** The current runs were made from committed `wp6-agent` code with a clean tree.
Each run's manifest names that exact commit (the *commit* column below). The first batch of runs
was made before `agent/` was committed, so their manifests name the base commit `235c883`. Those
runs are kept, labelled *pre-commit, superseded* (`results/case_study/superseded.json`), and listed
under *Superseded runs*. They are not used for the tables or the figure.

## Odd runs (kept)

- **Harness v1 (the first superseded run, sim backend).** llama3.1:8b returned all nine purchases as **one
  batch of parallel tool calls**. The wrapper executed them in well under a millisecond, before the
  harness thread could take the stop lock. So the stop fired after more than `k_stop` purchases, and
  once the batch was done the model only wrote a summary. The run has no post-stop agent call and
  fails the acceptance check. It is kept and listed above. The fix (harness v2, the stop handshake)
  was made before any Stripe run, and a regression test covers it
  (`agent/tests/test_case_study_sim.py::test_stop_fires_at_k_stop_inside_a_batch`). That
  change fixes a harness race against the spec ("after `k_stop` successful purchases"). It is not a
  change to the agent, the mandate or any runbook.
- **Every current run: one batch, then a summary.** In every current run the model issued the whole brief as
  one batch of parallel tool calls on its first turn. Its second turn was a plain-text summary.
  So the revoked agent's post-stop calls are the rest of that first batch: all of them DENIED, all
  at the stop instant, and all in the episode log because of the stop clock. No run shows the
  model *reacting* to a DENIED result with further calls. We did not change the brief or the
  prompt to provoke that.
- **A misspelled vendor** (one sim seed, in both its superseded and its current run; visible in the trace): the model wrote an allowlisted
  vendor's name with a typo in some calls. The mandate wrapper rejected them like any other
  off-list vendor, so that run has fewer post-stop DENIED calls than the others.
- **The agent's own report is wrong.** In every current run (and every superseded v2 run), the model's final reply overstates what was
  placed. It never mentions the revocation or a DENIED call, and some replies list items it never
  successfully ordered. In the superseded v1 run, the reply's count of placed orders disagrees with the log too.
  The table below covers the current runs; the superseded runs' replies are under *Superseded runs*. The table below compares each reply with the gateway log. The
  processor log is the evidence; the agent's own account is not.

- **Reruns reproduce the superseded runs.** With the same seeds and temperatures, each rerun's
  tool-call sequence (tools, arguments, order) is identical to its superseded v2 run's. Ollama's
  seeding makes this likely, not guaranteed.
- **The runbooks tie.** With so few pending payments, `k = 1` and the `low` fault preset, P3, P5 and
  P6 reach the same final states and loss in every run (policy table above). In the Fig. 1 run,
  one flagged payment's cancel cost equals its nominal capture time, and a capture wins a tie, so
  no runbook can cancel it in time. It also captured early (jitter). This is a demonstration of
  the chain, not evidence about runbook differences. The pre-registered holdout grid answers that.
- **Live vs replay:** the live P6 dispositions equal the simulator replay's in every run (runs
  table), including on Stripe. On Stripe, some captures fired slightly after their wall
  time because of HTTP latency (`max_lag_s` in each `summary.json`). Order and
  logical time are unaffected.

## Limitations

- **One model, one task, one brief.** A single 8B open-weights model (quantized, run locally) and
  one procurement brief. Nothing here generalizes to other models, prompts or tasks. Ollama's
  `seed` and `temperature` make runs repeatable in practice but not guaranteed byte-identical.
- **Test mode only.** Stripe test mode with a test card: no real money, cards or customers.
  Test-mode behaviour can differ from live mode, and the merchant capture is our emulator calling
  `capture` at a seeded `D_actual`, not a real merchant. **Simulated capture times are not
  card-network deadlines.**
- **The agent's batching shapes the trace.** The model tends to issue a whole brief as one batch
  of parallel calls. Post-stop calls are then mostly the rest of that batch, plus what the model
  does when it reads the DENIED results. The stop handshake briefly pauses the agent thread at
  the `k_stop`-th purchase; that pause is a harness artifact.
- **Comparisons are replays.** P3 and P5 are not run against Stripe here: each PaymentIntent can
  be disposed of once, so they run on the simulator with the same scenario and fault realization.
  WP5's conformance suite (C1) is the evidence that the simulator matches Stripe on these
  transitions; this case study does not add to it.
- **Tiny n, no statistics.** A handful of pending payments per run, a few runs. The per-policy
  losses are illustrations, not estimates; the pre-registered holdout results are the evidence.
- **Perfect containment is given.** Revocation is enforced at the gateway by construction (Liu et
  al., arXiv:2610.15991, define and study when revocation is complete; we cite, not claim, that
  ACK ≠ completion). The case study shows what is still open *after* that: pre-stop payments
  heading to capture.
- **Suspicion is a rule, not detection.** Labels come from a pre-declared vendor list. Nothing
  here evaluates fraud detection or the LLM's judgement.
